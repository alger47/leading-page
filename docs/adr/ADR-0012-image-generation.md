# ADR-0012: Stage 6 Image Generation (Hugging Face, ephemeral in-memory rasters) (Phase 16)

- **Status:** Accepted (2026-09-18, Phase 16)
- **Relates to:** ADR-0003 (AI engine pipeline), ADR-0004 (worker orchestration —
  §11.4 stable events, no new stable event added), ADR-0006 (web application);
  `docs/production-readiness.md` §image-generation; `docs/api-reference.md`.

## Context

Phase 16 adds value for ADS-N/A pages: instead of a placeholder-only media
experience, the pipeline can generate raster images for a landing page. Two
constraints drive the design:

1. **Free-tier cost discipline.** The platform runs on free tiers everywhere
   (Render services, Groq/Llama APIs). A per-image ComfyUI/Stable-Diffusion
   cluster is not viable; the cheapest *reliable* image generation today is the
   Hugging Face Inference API (byte-for-byte pay-as-you-go on FLUX.1-schnell,
   no GPU to host).
2. **No object storage yet.** There is no S3/compatible store in the free-tier
   stack. Persisting megabytes of PNGs in Postgres is unacceptable. Therefore
   generated bytes are **ephemeral by design**: cached in memory across three
   short-lived hops (engine → worker → web) and served memory-first; a
   deterministic placeholder is the honest fallback whenever bytes are gone
   (instance restart, eviction, disabled feature).

## Decision

**1. Stage 6 = `asset-renderer`, a code stage not an LLM stage.**
It runs after asset-planner (stage 5) inside `Pipeline.run` and produces a
deterministic prompt per `image`/`illustration` requirement
(`subject` + `orientation` + tone→style map, `_TONE_STYLE`). It is NOT a
free-typed stage: no schema consumption, no tokens, deterministic cost. It is
**OFF unless** `AI_IMAGE_PROVIDER` is enabled (`off` | `stub` | `huggingface`)
**AND** the request opted in with `generate_images: true`; when off it returns an
empty success (`{ "images": [] }`) so stage listings never drift.

**2. Bytes travel an ephemeral three-hop path; only refs enter the DB.**
`AssetRenderer.render()` returns `(StageResult, blobs)`. The pipeline stashes
blobs into `JobAssetStore` (engine, in-memory, cap 100, rebirth-proof) and puts
**only the manifest** (ref / mime / size_bytes / source) into `JobResult.assets`.
On COMPLETED the worker relays each ref via
`GET /internal/v1/assets/{job_id}/{ref}` into its `MemoryAssetStore`, then serves
`GET /api/jobs/:id/assets`. The web relays those bytes once at finalize into its
`RasterMemoryStore` and `/assets/asset/{ref}` serves them memory-first, else the
deterministic placeholder SVG. Refs stay logical (`asset:<requirement id>`,
§SEM-011) — the saved schema and DB never change shape.

**3. Honest failure, never a fake success.** A failing/missing/over-cap image
becomes a **warning issue `E-IMG-001`** on the stage (`draft=True`, page still
COMPLETES) and the ref keeps the placeholder. Image attempts are recorded in the
ledger with `model_class="image"`, `prompt_ref="image@<model_id>"`, and cost
`cost_per_image` (0 on failure); the job budget still guards overflow
(honest `E-AI-002`). Cap: `AI_IMAGE_MAX=4` images, `AI_IMAGE_MAX_BYTES=800_000` per
image, `kind` ∈ {image, illustration} (icons are not worth generating).

**4. No new worker stable event.** §11.4 stays untouched: stage events for the
web are derived from the existing engine-stage map; the asset manifest is a side
channel pulled at finalize. `POST_JOB_SCHEMA` gains `generateImages` (boolean,
`additionalProperties: false` preserved); `WorkerClient.getAssets` is **optional**
on the interface so the e2e in-process bridge fakes stay source-compatible.

**5. Deterministic cost model.** `images.default.cost_per_image` in each routing
config (0.0 in the shipped configs — HF free tier), prompt_refs recorded for
regeneration, latency captured per image. The ledger treats each image as one
attempt.

## Consequences

**Positive** — pages can ship real, phase-appropriate raster art without a GPU or
object store; the feature is deployable **OFF by default** (dashboards unchanged);
failure is bounded per-image and never fakes completion; the whole surface is
unit-tested end-to-end (engine 9 new tests / worker 3 new / web unit + 1 new
integration); no schema or DB migration.

**Trade-offs / notes** — raster bytes are ephemeral: reconstructed on a later job
(or by re-running the same brief, which is a new idempotency-key job) and lost on
restart, exactly like the in-memory job store; HF free tier is rate/latency
variable, hence per-image `E-IMG-001` + placeholder posture; no S3 persistence
until budget allows an object store (the `NEXT_PUBLIC_ASSET_S3_BASE_URL` host
override already exists as the upgrade seam). Image upload **is** still required
for stock/S3 swaps in the editor; generation only lowers media.dead time for a
fresh job.
