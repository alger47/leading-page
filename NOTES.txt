## Phase 8 Notes (Editor, section regeneration, validated drafts):

**Root-caused the "hanging" RegenerateJob — it was a store write race, NOT the engine.** Direct engine repro with the exact worker payload (ar brief, locale ar, tone warm-professional, budget 0.05, token test-token): GEN 200 @0.52s and REGEN 200 @0.41s COMPLETED. The bug: `apps/worker/src/jobs/enqueue.ts` did `await deps.queue.add(payload, { jobId })` THEN `deps.store.put(record)`. The in-memory driver's `void drain()` inside `add()` runs the processor *synchronously during add()*; the processor's `ensureRecord`/completion wrote RUNNING/COMPLETED, and enqueue's later `put` clobbered the same object (MemoryJobStore.byId returns live references) back to QUEUED → the status poll loop never saw terminal. **Fix: `store.put(record)` BEFORE `add()`, and try/catch on `add` failure → status FAILED, errorCode E-JOB-001, rethrow.** This is why the J2 e2e and web regen tests had to "look like they hang" — same root cause across stacks. The worker harness avoids it by resuming the paused bridge post-enqueue.

**Regen is a first-class job, not a special path.** `POST /api/v1/pages/:id/regenerate {versionNumber, targetSectionId, mode:'section'}` → a normal worker generation-jobs row (idempotent, liveSync, same error codes). The web builds a per-target payload; the engine runs the layout for just that section against the brief context. On COMPLETED, web persists a NEW version (saveVersion optimistic concurrency) whose non-target sections are byte-identical (asserted in the real-engine worker test). Failures → no version at all; the target stays intact.

**Editor architecture.** Generic shape-driven JSON editor over `latestVersion.content` (no per-section forms): string→input/textarea, number/boolean, arrays (add/remove/reorder, string or nested object items), objects→groups, `assetRef` objects (≤2 keys) → asset field with stock thumbnail grid + URL/alt inputs. `theme-picker` applies `{preset, font, primaryColor, radius, density}`. Preview renders the *draft* with the same ui-components Renderer as production.

**Keyed remount trick.** Server page: `<PageEditor key={'v'+versionNumber} ... />`. SAVE and regen-completion both call `router.refresh()`; the key change remounts a fresh editor on the new version. Trade-off: **regenerating a section discards unsaved local edits** (MVP, documented in ADR-0007).

**Themes/assets read shape gotcha.** `GET /api/v1/themes` returns presets where `preset` is TOP-LEVEL, not nested under `theme` (the theme preset object is `{preset, label, description, theme:{...}, swatches}`). A test asserting `theme.theme.preset` fails. Also: engine hero content is `{title, subtitle, primaryCta, secondaryCta, image:{assetRef,alt}}`, persisted as `media` after `_clean_hero` — real pages read `media.assetRef`. The web tests/harness.ts `samplePageSchema` uses `headline/subheadline` — TEST-ONLY fixture, never the real shape.

**Validation gates.** Save route: L1 structural check (same validator as generation finalize) → 422 `{error:{code:'E-VAL-L1', details:{issues:[{path,message}]}}}`; invalid envelopes never hit the DB. 409 E-CONFLICT when `baseVersion` is stale (optimistic concurrency; client must reload). ## Phase 9 Notes (Versioning — history, compare, restore; J4):

**Zero new persistence logic for restore.** `POST /pages/:id/versions/:v/restore` just reads the target snapshot and calls `PagesRepository.saveVersion({ baseVersion: latest, content: snapshot })` — immutability (new row), optimistic concurrency (409 → reload), and the L1 gate all apply exactly like an editor save. `restoredFrom` tells the UI what it came from. Restoring the latest onto itself is allowed (harmless identical new version). DB company rule from ADR-0005: versions are append-only; restore COPIES, never rewrites — verified end-to-end (v1..v3 all present, edited v2 untouched).

**Compare = pure `lib/versions-diff.ts`.** Structural deepEqual (JSONB re-orders keys, so string compare is WRONG — same lesson as the DB immutability tests). Sections matched by stable `id` (position is not identity — reorders would report everything "changed"); entries carry `action: added|removed|unchanged|changed`, `previousPosition/currentPosition`, and `changedSlots` (`content.title`, `variant`, …). Metadata diffs `title/locale/direction/theme` as `{previous, current, changed}`. The compare ROUTE reuses the same function, so API/e2e and UI agree; unit tests cover the function directly (incl. pathological non-envelope input without throwing).

**Harness bug worth remembering (test-only).** The web test harness builds NextRequest from `http://localhost${path}` and dispatches by regex. Query strings were NOT stripped before matching: `versions/compare?from=1&to=2` fell through to the `:v` detail route (`versionNumber='compare?...'` → 400), and restore/compare never got their `params`. Fix: `routeFor`/`paramsFor` match on `path.split('?')[0]` and extract compare + restore params. nextUrl.searchParams itself DOES carry the query (probed with tsx) — the bug was pure dispatch.

**First-version restore semantics.** The J4 e2e: generate v1 (real engine+worker), POST an edited envelope → v2 (same route the editor uses), compare 1 vs 2 → title + `content.title` changed, restore v1 → v3 byte-equal (toEqual structural) to v1's snapshot. This is the same edit path a user exercises in the Versions UI.

**Version list is metadata-only** in the list endpoint (content excluded); use `GET /versions/:v` for the full snapshot. Compare is server-side; the UI just renders `{ from, to, diff }`.

## Phase 10 Notes (publishing):

**Publish gate is two-tier (L1 structural AND L2 semantic).** SEM errors (SEM-001..004) are advisory for DRAFTS (save gate = L1 only) but HARD for publishing. The gate lives in lib/publishing.ts (PublishGateError / E-PUBLISH-001, 422 + details.issues), not in a repository. Test trick used everywhere: the harness publishableEnvelope({footer:false}) fixture is L1-valid but L2-invalid (SEM-004) - it must save as a draft and then fail the publish gate.

**Host stability.** deriveHostForPage(pageId) = p-<pageId-last-12-alnum-lowercase>.<PUBLIC_HOST_SUFFIX>; URL = PUBLIC_BASE_URL/<host>. Republishing a newer version moves the Page.subdomain pointer - the host NEVER changes (no new subdomain rows). DELETE (unpublish) detaches idempotently; republish after unpublish recreates at the SAME host.

**React context vs Server Components (the build blocker).** The shared ui-components <Render/> needs ThemeProvider (React.createContext), and the react-server webpack build strips createContext -> `next build` fails with "TypeError: i(...).createContext is not a function ... Failed to collect page data for /[host]". The public route therefore renders through ONE thin client shell (components/published-page.tsx, 'use client', importing ONLY @landing-ai/ui-components). Everything else on the route stays server-side (getPublishedViewByHost + generateMetadata). The "zero dashboard/editor JS" guarantee = no dashboard/editor modules in the published bundle (two independent checks: unit isolation test on source + marker scan of the BUILT server bundle).

**react-dom/server is banned in page-imported modules** ("You're importing a component that imports react-dom/server"). SSR assert helper lives in test-only tests/render-html.ts (renderPublishedHtml -> renderToStaticMarkup(<Render/>)).

**Budget measurement is fetch-set, not all-chunks.** v1 of scripts/published-budget.mjs summed EVERY webpack-emitted chunk (incl. the dashboard page chunk, generation-view, editor lazy chunks) -> fake 208.8 KB fail. The real browser fetch-set for (published)/[host] is: webpack-{hash}.js + framework-{hash}.js + main-{hash}.js (entry; carries the renderer) + main-app-{hash}.js + the tiny page-{hash}.js chunk under app/(published)/[host]/ -> 79.5 KB gzipped (90 KB budget). Legacy polyfills-{hash}.js is browser-conditional (old Engine) - reported separately, excluded. Dashboard/editor modules land in separate numbered lazy chunks NOT fetched by the public page (verified: main contains no editor markers).

**API quirks worth remembering:**
- Empty-body POST publish returns 400 if you `await request.json()` unconditionally -> read `request.text()`, JSON.parse only when non-empty. Empty body means "publish/latest".
- routeFor/paramsFor in the harness must match the FULL path including the publish segment (regex ^/api/v1/pages/[^/]+/publish$); the draft-validate helper writes versions ONLY via the publish gate's canPublish path so fixtures are honest.
